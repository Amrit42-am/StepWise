STEPWISE DSA
Project Specification / Hackathon Documentation

Project Name:
StepWise DSA

Tagline:
"Learn the approach, not the answer."

------------------------------------------------------------
1. PROJECT OVERVIEW
------------------------------------------------------------

StepWise DSA is an AI-powered DSA learning assistant designed to help
students solve Data Structures and Algorithms problems without directly
giving them the final solution.

The main idea is simple:

Instead of asking AI:
"Give me the code."

the student asks:
"Help me figure out how to solve this."

StepWise responds with a sequence of conceptual steps and progressive
hints. The student is encouraged to think, try, make mistakes, and
improve their own solution.

The project also has a second mode where a student submits their own
code. In this mode, the AI reviews the code and gives hints about the
problem without directly rewriting the code or giving the complete
solution.

The product is intended to feel like a patient DSA mentor rather than
a code-generation tool.


------------------------------------------------------------
2. THE PROBLEM
------------------------------------------------------------

Many students use AI coding tools while learning DSA. A common problem
is that these tools immediately provide:

- the algorithm
- the optimized approach
- the complete code
- the final answer

This can solve the immediate problem, but the student may not learn how
to arrive at the solution independently.

For DSA practice, the important skill is not only knowing the final
algorithm. It is learning how to:

1. Understand the problem.
2. Identify what is being asked.
3. Think of a brute-force approach.
4. Identify inefficiencies.
5. Choose the correct data structure.
6. Optimize the approach.
7. Analyze time and space complexity.
8. Convert the idea into code.
9. Debug their own mistakes.

StepWise DSA focuses on this reasoning process.


------------------------------------------------------------
3. CORE IDEA
------------------------------------------------------------

StepWise DSA has two main capabilities.

A. APPROACH MODE

The student provides a DSA problem.

The AI does NOT immediately solve it.

Instead, it breaks the thinking process into steps.

Example:

Problem:
"Given an array and a target, find two numbers whose sum equals
the target."

Step 1:
Understand what information is available and what needs to be found.

Step 2:
Think about what would happen if every possible pair were checked.

Step 3:
Identify why checking every pair may be inefficient.

Step 4:
Think about what information could be stored while traversing the
array.

Step 5:
Choose a data structure that allows fast lookup.

Step 6:
Think about the resulting time complexity.

The user is expected to derive the final algorithm themselves.


B. CODE HINT MODE

The student submits their own code.

The AI analyzes the code and provides hints rather than replacing it.

Example:

Student code:
A nested loop solution for Two Sum.

AI response:
Hint 1:
"Look at how many times you are checking pairs."

Hint 2:
"Is there information from previous elements that you could remember?"

Hint 3:
"Can you use a data structure that gives fast membership lookup?"

The AI should guide the student toward the issue without writing the
complete optimized solution.


------------------------------------------------------------
4. MAIN OBJECTIVE
------------------------------------------------------------

The objective is to create an AI mentor that teaches problem-solving
rather than simply generating answers.

The product should optimize for:

- learning
- reasoning
- independent problem solving
- debugging
- progressive guidance

The product should NOT optimize for:

- fastest code generation
- giving complete solutions immediately
- replacing the student's thinking


------------------------------------------------------------
5. AI BEHAVIOR
------------------------------------------------------------

The AI is the most important part of the project.

It should behave as a DSA mentor.

General behavior:

1. First understand the student's goal.
2. Explain concepts in simple language.
3. Give one useful step at a time.
4. Avoid unnecessarily advanced terminology.
5. Encourage the student to think before revealing more.
6. Adapt the next hint based on the previous interaction.
7. Avoid giving the complete solution by default.
8. Avoid writing complete working code unless the user explicitly
   asks for a final solution and the product allows it.
9. When reviewing code, point out the area of concern rather than
   rewriting the entire code.
10. Explain why a hint matters when necessary.

The AI should prefer questions such as:

- "What happens if we check every pair?"
- "What is causing the O(n^2) complexity?"
- "Can you remember something about elements you've already visited?"
- "Which data structure could make this lookup faster?"
- "What happens at the boundary of your loop?"
- "What happens when the input is empty?"

This makes the student reason rather than copy.


------------------------------------------------------------
6. PROGRESSIVE HINT SYSTEM
------------------------------------------------------------

Hints should become stronger gradually.

Suggested levels:

LEVEL 1 - CONCEPTUAL HINT
Very small clue that points the student in the right direction.

LEVEL 2 - DIRECTION HINT
Points toward a type of idea or strategy.

LEVEL 3 - DATA STRUCTURE / ALGORITHM HINT
Suggests the relevant technique without providing the full solution.

LEVEL 4 - IMPLEMENTATION HINT
Points toward how the idea can be translated into code.

LEVEL 5 - PSEUDOCODE-LEVEL GUIDANCE
Gives a stronger structure while still avoiding a full final code
solution.

The normal experience should stop before complete solution generation.


------------------------------------------------------------
7. APPROACH MODE - EXPECTED AI PROCESS
------------------------------------------------------------

When a problem is given, the AI should generally follow this reasoning
sequence:

Step A:
Identify inputs and outputs.

Step B:
Clarify what the problem is asking.

Step C:
Consider simple/brute-force reasoning.

Step D:
Estimate brute-force time and space complexity.

Step E:
Identify the bottleneck.

Step F:
Ask what information can be stored or reused.

Step G:
Consider possible data structures or algorithmic patterns.

Step H:
Guide the student toward an improved approach.

Step I:
Ask the student to state the approach in their own words.

Step J:
Only provide stronger implementation guidance if required.


------------------------------------------------------------
8. CODE HINT MODE - EXPECTED AI PROCESS
------------------------------------------------------------

When code is submitted:

1. Understand the intended approach.
2. Identify syntax errors, logical errors, complexity issues, or edge
   cases.
3. Determine whether the current approach is brute-force, optimized,
   or partially correct.
4. Give the smallest useful hint first.
5. Let the student attempt a correction.
6. Give a stronger hint only if requested.
7. Never silently replace the student's code with a complete solution.

Examples of useful hints:

"Check your loop boundary."

"You are reading the previous index before it is valid."

"Your approach works, but the repeated search is making it O(n^2)."

"Think about whether this value needs to be recalculated."

"Consider what happens when the input contains duplicates."

"Your base case does not cover an empty input."

"Your pointer movement may cause one element to be skipped."


------------------------------------------------------------
9. EDGE CASES THE AI SHOULD ENCOURAGE
------------------------------------------------------------

Depending on the problem, the AI should remind students to think
about:

- empty arrays
- single-element arrays
- duplicate values
- negative numbers
- already sorted input
- reverse-sorted input
- very large inputs
- duplicate answers
- impossible cases
- integer overflow
- null or missing values
- recursion base cases
- pointer boundaries
- disconnected graph components

The AI should not list every edge case automatically. It should
surface the relevant ones at the appropriate stage.


------------------------------------------------------------
10. OPEN-SOURCE AI
------------------------------------------------------------

The project uses Gemma as the open-weight AI model at the core of the
learning experience.

The AI is not an optional chatbot added to the project. Its mentoring
behavior is the actual product functionality.

Using an open model provides control over the instruction and behavior
of the mentor.

The system can define strong rules such as:

- Do not reveal the final solution immediately.
- Use progressive hints.
- Encourage reasoning.
- Analyze the student's own code.
- Adapt the strength of hints.
- Allow the model to be changed or adjusted later.
- Potentially run the model locally when hardware permits.

This makes the open approach meaningful to the project.


------------------------------------------------------------
11. WHY OPEN INNOVATION MATTERS
------------------------------------------------------------

The learning behavior of StepWise DSA needs to be controlled by the
developer.

A closed coding assistant may be optimized to satisfy a user quickly
by producing a complete answer. StepWise DSA needs a different
behavior: it needs to deliberately avoid solving the problem too early.

An open-weight model makes it easier to:

- control the mentor instructions
- modify the system behavior
- experiment with different prompting strategies
- swap models later
- potentially run inference locally
- keep more control over how student code is processed
- avoid building the entire product around a single closed model API

The important point is that the open model enables the teaching
behavior instead of simply powering a generic chatbot.

12. MONGODB ATLAS
------------------------------------------------------------

MongoDB Atlas can be used as the application's data layer.

Possible data stored:

User:
- user ID
- optional name
- learning preferences

Problem session:
- problem statement
- difficulty
- topic
- current hint level
- number of hints requested
- current progress

Code session:
- submitted code
- programming language
- detected issue category
- hint history

Learning history:
- solved problem topics
- common mistakes
- previous attempts
- areas where the student repeatedly needs hints

The database should store only the information needed by the product.

16. IMPORTANT AI RULES
------------------------------------------------------------

The AI system prompt should enforce the following principles:

1. Act as a DSA mentor, not a code generator.
2. Do not give the complete solution immediately.
3. Do not reveal the final algorithm too early.
4. Prefer questions and hints over direct answers.
5. Give progressive hints.
6. Start with conceptual guidance.
7. Only become more specific when the student requests another hint
   or is clearly stuck.
8. When reviewing code, preserve the student's ownership of the code.
9. Point out errors without automatically rewriting everything.
10. Explain complexity only when relevant.
11. Encourage the student to state their own understanding.
12. Avoid unnecessarily long explanations.
13. Never pretend that an incorrect idea is correct.
14. If the student's reasoning is wrong, explain what part needs to be
    reconsidered without immediately revealing the final solution.

17. EXAMPLE COMPLETE SESSION
------------------------------------------------------------

Problem:
"Given an array of integers and a target, return the indices of two
numbers whose sum equals the target."

AI:

Step 1:
"What would happen if you compared every possible pair?"

Student:
"That would work but it would take O(n^2)."

AI:

Step 2:
"Good. What causes the O(n^2) behavior?"

Student:
"We repeatedly search through the array for another value."

AI:

Step 3:
"Can you store information about values you've already visited?"

Student:
"Maybe a hash map?"

AI:

Step 4:
"Exactly. Before moving to code, what would you store in the map?"

Student:
"The number and its index."

AI:

Now the student has essentially discovered the approach without receiving
the complete solution.


------------------------------------------------------------
18. EXAMPLE CODE HINT SESSION
------------------------------------------------------------

Student submits:

for(int i = 0; i < n; i++) {
    for(int j = i + 1; j < n; j++) {
        if(arr[i] + arr[j] == target)
            return {i, j};
    }
}

AI:

Hint 1:
"Your code is logically reasonable, but look at the number of pair
comparisons."

Student requests another hint.

Hint 2:
"Can you avoid searching through the remaining array again for every
element?"

Student requests another hint.

Hint 3:
"What data structure could help you check whether the value you need
has already appeared?"

The AI still does not write the complete optimized code.


------------------------------------------------------------
19. MVP SCOPE
------------------------------------------------------------

The first version only needs:

1. Approach generation for a DSA problem.
2. Progressive hints.
3. Code hint mode.
4. Gemma integration.
5. Basic session storage in MongoDB Atlas.
6. Deployment through Render.

Everything else is optional.


------------------------------------------------------------
20. THINGS NOT REQUIRED FOR THE MVP
------------------------------------------------------------

Do NOT make the first version unnecessarily large.

Not required:

- social networking
- leaderboards
- complicated authentication
- video lessons
- payment system
- large problem database
- competitive programming platform
- automatic code submission judge
- voice assistant
- advanced analytics
- complex AI agents
- multiple models at launch

The core experience should remain:

"Give me a problem -> guide my thinking."

and

"Here is my code -> give me a hint."


------------------------------------------------------------

Later versions can add:

------------------------------------------------------------
22. SUCCESS CRITERIA
------------------------------------------------------------

The project is successful if a student can:

1. Enter a DSA problem.
2. Receive a useful first step instead of the answer.
3. Request additional hints progressively.
4. Develop an approach independently.
5. Paste their code.
6. Receive useful debugging hints.
7. Improve their own code without the AI automatically replacing it.

The most important success metric is:

"Did the AI help the student think?"

rather than:

"Did the AI solve the problem?"


------------------------------------------------------------
23. ONE-LINE DESCRIPTION
------------------------------------------------------------

StepWise DSA is an open-AI DSA mentor that teaches students how to
arrive at a solution through step-by-step reasoning and progressive
code hints instead of immediately giving the answer.


------------------------------------------------------------
24. HACKATHON PITCH
------------------------------------------------------------

"Most AI coding tools are built to give you the answer. StepWise DSA is
built to make you think. A student can enter a DSA problem and receive
a guided sequence of hints that leads them toward the approach without
revealing the final solution. They can also paste their own code and
receive targeted hints about what is wrong or inefficient. Gemma powers
the mentoring behavior, MongoDB Atlas stores learning sessions, and
Render hosts the application. The open model matters because we can
control the AI's behavior and make it act like a mentor rather than a
code generator."


------------------------------------------------------------
25. FINAL PRODUCT PRINCIPLE
------------------------------------------------------------

The central rule of StepWise DSA is:

"Help the student reach the answer.
Do not simply give the student the answer."

That principle should guide the AI prompts, backend logic, testing, and
future development of the project.
